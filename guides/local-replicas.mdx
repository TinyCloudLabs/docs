<Note>
**Beta feature in the stable packages.** Local replica behavior and the on-disk
format may change in a minor release.
</Note>

A local replica is a durable, read-only copy of the latest values under one KV
prefix. Sync it while online, then read that prefix from the device while offline.
It is not offline writes, and it is not a replica of SQL data.

## Requirements

- The TinyCloud node must advertise `kv-sync-v1` in its `/info` response. The
  production node at `tee.node.tinycloud.xyz` advertises this feature.
- Install the stable CLI (version 1.1.0 or later):

  ```sh
  npm i -g @tinycloud/cli
  ```

- CLI replicas need Node.js 22.13 or newer, or Bun. SQLite rejects older Node
  versions; Bun supplies its own SQLite runtime.
- For browser apps, install and pin an exact replica package version. For
  example, use `@tinycloud/replica@0.1.0`.
- A device needs a grant that covers its configured KV prefix and includes
  `get` and `sync`. `list` and `metadata` are optional.

## CLI: grant, sync, and read offline

### 1. Grant the device access to one prefix

Create or select a device profile and make it request access to the narrowest
prefix it needs. For example, the `device` profile requests `get` and `sync`
access to `notes/`:

```sh
tc profile create device --posture delegate-session
tc --profile device auth request \
  --cap "tinycloud.kv:<SPACE_ID>:notes/:get,sync" \
  --expiry 30d --emit request.json
```

The space owner reviews and grants that request, then the device imports the
grant. Run the owner command in the owner's profile; import the resulting
artifact in the device profile:

```sh
tc --profile owner auth grant request.json --yes > grant.json
tc --profile device auth import grant.json
```

`sync` is an explicit capability: a grant for ordinary KV reads alone is not
enough. The replica stores only its configured prefix, which must be covered
by the grant; the grant may cover a broader prefix.

### 2. Sync the prefix

Run the first sync with the desired prefix. The CLI creates a local replica
named after that prefix unless you supply `--replica`:

```sh
tc --profile device replica sync --prefix notes/
```

Later, run `tc --profile device replica sync` again to poll for updates and
deletes. The configured source host, space, and prefix are fixed for that
replica. Use a different `--replica` name if you need a different scope.

### 3. Read while offline

First log in with the device profile and its grant:

```sh
tc --profile device auth login
```

The grant must authorize the configured prefix. For a secrets-space or `vault/`
prefix, login also requires `--replication-allow-secrets`; otherwise it fails
with `SECRETS_OPT_IN_REQUIRED` (exit 2). Runtime grants can also provide
authority when the node-sdk is used.

`get` and `list` read only from local replica storage; they never fall back to
a host KV request. Stop the network or disconnect, then run:

```sh
tc --profile device replica get notes/today.txt
tc --profile device replica list notes/
```

Use `--raw` to write the value bytes to standard output, or `-o file` to save
them to a file. Sync must have completed the initial prefix coverage before
you can rely on reads of keys that have not yet been observed.

### 4. Inspect or reset local data

```sh
tc --profile device --replication replica report
tc --profile device replica reset
```

`tc --profile device --replication replica report` reports live replica status,
including scope, sync state, authority, counts, and failures. `reset` clears
entries, content, and the cursor but keeps the replica configuration and grant,
so sync can populate it again. Add `--purge` to remove that replica entirely:

```sh
tc --profile device replica reset --purge
```

### Command options

| Command | Options | Behavior |
| --- | --- | --- |
| `replica sync` | `--replica <name>` | Select a replica; without it, the CLI uses the profile's only replica or names a new one from the first-sync prefix. |
| `replica sync` | `--space <id\|name>`, `--prefix <prefix>` | Set the space and prefix on first sync. The prefix is required; later syncs keep the original scope. |
| `replica sync` | `--limit <n>` | Set feed page size from 1 to 1000. |
| `replica sync` | `--allow-secrets` | Explicitly allow a secrets-space or `vault/` replica; see the security warning below. |
| `replica sync` | `--retention-grant <cid>` | Use an owner-issued `tinycloud.kv/retain` grant; see [Retaining reads after grant expiry](#retaining-reads-after-grant-expiry). |
| `replica get <key>` | `--replica <name>` | Select the replica. |
| `replica get <key>` | `--raw` or `-o, --output <file>` | Write raw bytes to stdout or atomically to a private output file. |
| `replica get <key>` | `--no-verify` | Skip the stored-content hash check; leave verification enabled unless you have a specific reason not to. |
| `replica list [prefix]` | `--replica <name>`, `--after <key>`, `--limit <n>` | Select the replica and paginate local keys after a key, optionally limiting the result count. |
| `replica status` | `--replica <name>` | Show one replica; omit it to show all replicas in the profile. |
| `replica reset` | `--replica <name>`, `--purge` | Select a replica; `--purge` removes it instead of clearing its entries and cursor. |

Pass the global `--host <url>` when creating a replica if the profile has no
default host; the chosen source is pinned to that replica.

For example, after confirming that storing encrypted secret material locally
is acceptable:

```sh
tc --profile device replica sync --prefix vault/ --allow-secrets
```

This flag only opts in to copying ciphertext. It does not grant decrypt access.

### Retaining reads after grant expiry

By default, local reads are allowed only while the device's sync grant is
valid. An owner may separately issue a `tinycloud.kv/retain` grant to authorize
a bounded retention window for already-synced local reads after that sync grant
expires. Supply the retention grant's CID during a sync:

```sh
tc --profile device replica sync --retention-grant <RETENTION_GRANT_CID>
```

The node attests the permitted retention window. This does not extend the
sync grant or allow new syncs after it expires. A learned revocation still
blocks reads. Omit the option to use the default policy.

### Error codes and next steps

The CLI prints a machine-readable error code alongside the message. Common
replica errors:

| Code | Meaning | What to do |
| --- | --- | --- |
| `NOT_COVERED` | The key is outside this replica's prefix. | Read from an authorized source or sync the intended prefix with a separately scoped replica. |
| `KEY_DELETED` | The replica holds a tombstone for a key deleted at the source. | Recreate the key at the source, then sync to fetch its value again. |
| `KEY_ABSENT` | The key is not in a replica with complete prefix coverage. | Check the key or source data; syncing will not help if it was never present. |
| `COVERAGE_INCOMPLETE` | The first sync has not finished covering the prefix. | Run `tc replica sync` until coverage completes. |
| `CONTENT_MISSING` | The key is known, but its content is not stored locally. | Run `tc replica sync` to fetch it. |
| `GRANT_MISSING` | No usable device grant is installed. | Request and import a grant with the required prefix and capabilities. This also occurs when stored grants are malformed, for another audience, insufficient for this prefix, not yet valid, or expired; unusable grants are filtered out. |
| `GRANT_EXPIRED` | The device grant's authority window ended. | Renew the grant and sync again. To retain local reads after expiry, configure retention and sync while the sync grant is still valid; an expired grant cannot obtain a new retention attestation. |
| `GRANT_REVOKED` | The node reported that the grant was revoked. | Ask the owner for a new grant; revoked authority cannot be restored by retrying the old grant. |
| `SECRETS_OPT_IN_REQUIRED` | The requested scope includes the secrets space or a vault namespace. | Reconsider whether encrypted secret material should be stored on this device; only then use `--allow-secrets`. |
| `NETWORK_ERROR` | Sync could not reach the pinned host. | Reconnect to the host and retry sync; local reads remain separate from sync. |
| `STORAGE_FULL` | Local storage could not accept the data. | Free device storage and retry. |

Other errors identify configuration, grant, storage, or node failures:

| Code | Meaning | What to do |
| --- | --- | --- |
| `REPLICA_CONFIG_MISMATCH` | An existing replica name is already pinned to a different space, prefix, or host. | Use another `--replica` name, or reset it with `--purge` before recreating it. |
| `GRANT_INVALID`, `GRANT_FORMAT_UNSUPPORTED` | The installed grant is malformed, has an invalid signature, or is not a UCAN. | Import a valid UCAN delegation issued for the device. |
| `GRANT_AUDIENCE_MISMATCH` | The grant is addressed to another device. | Ask the owner to issue a grant for this profile's device. |
| `GRANT_NOT_COVERING` | The grant lacks the required `get` or `sync` ability on the prefix. | Request unrestricted `tinycloud.kv/get` coverage of the folder prefix (or broader) and explicit `tinycloud.kv/sync` on that prefix (or broader); wildcard grants do not include `sync`. Exact-key grants never cover a folder prefix. |
| `GRANT_NOT_YET_VALID` | The grant's validity window has not started. | Wait until it becomes valid, then sync again. |
| `GRANT_UNAUTHORIZED` | The node refused the grant for a reason other than revocation. | Check the grant scope and node authorization; ask the owner to issue the intended access. |
| `RETENTION_GRANT_REFUSED` | The node refused the retention grant. | Check that its CID names a valid `tinycloud.kv/retain` grant for this replica. |
| `REPLICA_BUSY` | Another process is syncing or modifying this replica. | Wait for it to finish, then retry. |
| `RUNTIME_UNSUPPORTED` | The runtime cannot provide the replica's durable local storage. | Use a supported runtime. |
| `STORAGE_ERROR` | Local storage failed, for example because of I/O or corruption. | Resolve the device storage problem before retrying. |
| `NODE_ERROR`, `PROTOCOL_ERROR` | The node returned an error or an unexpected sync response. | Check node health and version support, then retry; report persistent failures. |
| `RESET_REQUIRED` | The node requires the replica to bootstrap again. | Sync automatically retries once from a fresh bootstrap. If the error still reaches you, investigate the node, or reset the replica and sync again. |
| `SOURCE_CHANGED` | The replica's pinned source node differs from the responding node. | Sync against the original host or create a separate replica for the new source. |
| `SCOPE_VIOLATION` | The feed included a key outside the configured prefix. | Stop using this replica and report the node/protocol failure. |
| `CONTENT_MISMATCH`, `INTEGRITY_ERROR` | Downloaded or stored content failed its integrity check. | Do not use the value; retry sync and report a persistent mismatch. |
| `REPLICA_NOT_FOUND` | The selected replica name does not exist. | Sync with its `--prefix` to create it, or choose an existing replica. |

Exit codes: `0` success; `1` busy/runtime/storage error; `2` usage, invalid
replication prefix, outside-scope or caveated prefix, or `SECRETS_OPT_IN_REQUIRED`;
`3` missing or invalid grant; `4` absent, deleted, missing-content, or
incomplete-coverage key; `5` expired, revoked, or not-yet-valid grant; `6`
network; `7` node, protocol, or integrity error; `10` local storage full.

## Read-through flag (beta): CLI and node-sdk

This Phase 1 read-through beta is separate from the explicit `tc replica` commands above. It routes eligible `node.kv.get()` and `node.kv.list()` calls through a local replica, falling back to the unchanged network request when the replica cannot safely answer. It is opt-in and applies only to primary-space KV. Browser `web-sdk` read-through is covered in [Web read-through](#web-read-through-beta-web-sdk).

### Enable read-through

The CLI flag enables read-through for one invocation; it does not select prefixes. Save one or more prefixes during login so later invocations can use them:

```sh
tc auth login --replication-prefix notes/
tc --replication kv get notes/today.txt
```

`--replication` or `TC_REPLICATION=1` enables read-through; the environment
variable sets the default to on. `--no-replication` disables it even when
`TC_REPLICATION=1` is set. The feature is off by default.
`tc auth login --replication-prefix <prefix>` is repeatable; an explicit list
replaces the saved prefixes, while omitted options reuse saved prefixes on
later logins and key rotation. Without a saved prefix, the CLI has nothing to
replicate.

For a node-sdk client, enable the option and provide storage explicitly:

```ts
import { TinyCloudNode, sqliteReplicaStorage } from "@tinycloud/node-sdk";

const node = new TinyCloudNode({
  replication: {
    enabled: true,
    prefixes: ["notes/"],
    storage: sqliteReplicaStorage({ dir: "./.tinycloud-replicas" }),
  },
});
```

`enabled` requires a non-empty `prefixes` array and `storage`; overlapping prefixes are rejected. The Node SQLite adapter requires Node.js 22.13 or newer (or Bun). `sqliteReplicaStorage({ dir, guard })` accepts an optional `guard` for serialized storage mutations. `node.replication` exposes `status()`, `sync()`, `purge()` and `clearPending()`.

The status output gains `purge_pending`, which reports partitions with an unfinished erase, and `persisted`, the result of `navigator.storage.persist()` in browsers.

There are **no default prefixes**. A replication prefix is a folder: non-empty,
slash-terminated, with no leading slash or empty path segments (for example
`notes/` or `notes/private/`), or `/` for the whole space. `""`, bare paths
such as `notes`, `/notes/`, and paths containing `//` are invalid. CLI login
rejects these with `INVALID_REPLICATION_PREFIX` and exit 2; the node-sdk
rejects invalid configuration with a `TypeError`, and replica APIs report
`REPLICA_INVALID_ARGUMENT`. Bare prefixes persisted by 3.1.0 replicas are no longer accepted. Purge an explicit CLI replica with `tc replica reset --replica <name> --purge`, then recreate it with `--prefix notes/`. Replace a saved CLI read-through prefix at login with `tc auth login --replication-prefix notes/`.

Replication requires unrestricted `tinycloud.kv/get` authority covering the
entire folder prefix (or broader) and explicit `tinycloud.kv/sync` on that
prefix (or broader); wildcards never grant `sync`. An exact-key grant never
qualifies. Owner logins using a local key or OpenKey that already have
unrestricted whole-space `get` add `sync` once to the whole-space KV entry,
regardless of the number of configured prefixes. Delegated and device sessions
need `sync` authority on the prefix (or broader) in their grant. CLI login refuses a prefix without unrestricted covering `get` with `REPLICATION_PREFIX_OUTSIDE_SCOPE` or `REPLICATION_PREFIX_CAVEATED` (exit 2). The node-sdk instead skips sync augmentation for that prefix; it needs sufficient authority before the replica can serve local reads. For CLI read-through, `vault/` and `/` require `--replication-allow-secrets` at login, otherwise login fails with `SECRETS_OPT_IN_REQUIRED` (exit 2). For node-sdk, set `replication.allowSecrets: true` for either prefix; otherwise construction throws a `TypeError`.
`/` selects the whole space and includes `vault/`, so it also requires
`--replication-allow-secrets`. Whole-space sync requires a node advertising
`kv-sync-root` in `/info` (tinycloud-node 1.20.1 or later). On older nodes,
root replication fails with `REPLICATION_ROOT_UNSUPPORTED`, and replica
status reports that same code as unavailable.



LIST coverage follows the actual list path. A `notes/` replica serves
`node.kv.list({ prefix: "notes/" })` and nested lists locally. In contrast,
`node.kv.withPrefix("notes").list()` uses path `notes`, which is not covered
by a `notes/` replica and falls back to the network. A `/` replica serves any
list locally. A pending write in the unread portion of a list range forces network fallback; with a local continuation cursor, it instead returns `INVALID_INPUT` with `meta.replication: "cursor_restart"`. Restart the list without that cursor.

### Where reads go

An eligible local answer requires the replica selection and current unrestricted authority to cover the whole key or list range, complete coverage, no pending-write pin for the key or list range, and no failed stale-sync attempt that requires a network fallback. A list path `P` covers the key `P` and descendants under `P/`; a pending write in the unread portion of that range forces network fallback or, with a local continuation cursor, returns `INVALID_INPUT` with `meta.replication: "cursor_restart"`. A stale local value can still be used when the bounded sync fails offline. The table gives common outcomes; network fallback returns the network result, not the replica result.

| Condition | Read source | Reason or result |
| --- | --- | --- |
| Covered, complete, authorized replica has the key | Local | `hit` |
| Covered and complete replica knows the key is absent or deleted | Local | `absent` or `deleted` |
| No configured prefix covers the key or complete list range | Network | `not_covered` |
| Initial sync has not completed, or local content is missing | Network | `coverage_incomplete` or `content_missing` |
| No usable, unrestricted runtime grant for this prefix at read time | Network | `grant_missing` |
| A pending write pins the key or list range | Network | `pending_write` |
| The replica has not synced through a committed write's epoch | Network | `REPLICA_BEHIND_OWN_WRITES` |
| A required stale sync is busy or fails with a non-network error | Network | `stale` |
| Replica runtime cannot provide supported storage | Network | `runtime_unsupported` |
| Other replica-open failure, including invalid or mismatched storage | Network | `replica_unavailable` |
| Stale sync fails with `NETWORK_ERROR` or reaches its timeout, the drained sync has settled, status refresh succeeds, and local coverage, authority and pending-write checks still pass | Local | `hit`, `absent` or `deleted`, with `syncError` |

Other network fallback reasons include `replica_error` (local read or storage failure), `unsupported_option` (for example, an oversized `get` under `maxResponseBytes` or raw `list`), and `network_cursor` (a node-issued list cursor). Events are available through the SDK's `onEvent` callback; the CLI can print per-read and sync diagnostics with `--replication-debug`. A local `tcr1.` continuation that cannot be served safely returns `INVALID_INPUT` with `meta.replication: "cursor_restart"` instead of making a network request; see [List ordering and cursors](#list-ordering-and-cursors).

### Freshness and offline reads

On a stale read, the SDK tries a sync before using the local answer. The node-sdk defaults are a 120-second maximum staleness and a 5-second stale-sync timeout. CLI foreground mode has no background timer; defaults are 60 seconds and 10 seconds. Override the CLI values per process:

```sh
TC_REPLICATION_MAX_STALENESS_MS=30000 \
TC_REPLICATION_SYNC_TIMEOUT_MS=3000 \
tc --replication kv get notes/today.txt
```

When offline, an eligible stale value (or authoritative absent/deleted result) can be served locally after the sync reports a network error or times out; its read event includes `syncError: "NETWORK_ERROR"` or `"TIMEOUT"`. An unresolved pending write, incomplete coverage, or unusable authority still prevents a local answer. Without a local answer the SDK uses the network path and that request can fail. **Known limitation (TC-897):** offline CLI network errors currently exit 1, not 6.

### Read-your-writes and pinned keys

Read-your-writes protection applies only to writes made while read-through is enabled. A write made while the flag is off creates no pending record; it is treated like a write from another device and may appear after a later sync.

With the flag on, a committed write stays protected until a sync that started after its commit catches up. A write with an unknown outcome (`ambiguous`), or an unfinished `in_flight` write, pins its key to the network. Matching content, absence, or a later write does not resolve an ambiguous outcome; it remains pinned until explicitly cleared or purged. A pin means the read does not get a stale local result, even when offline. `tc --replication replica report` shows pinned keys, state, operation, `since`, error code and whether an in-flight record is likely orphaned.

### Inspect, clear, and purge

```sh
tc --replication --replication-debug kv get notes/today.txt
tc --replication replica report
tc --replication replica report --json
tc --replication replica report --clear-pending
tc --replication replica report --purge
```

The report summarizes reads by source and reason, hit ratio, latency and staleness percentiles, syncs, writes, divergences, live replica status, pinned keys, and other local identity partitions. `--since <duration>` selects the event window (default `24h`); `--json` emits structured output, including the `since` window value.

`--clear-pending` clears unresolved ambiguous and likely-orphaned in-flight records for the current identity. It prints a warning first: clearing stops pinning keys whose write outcome was unknown; if that write committed or commits later, an older local value can be served until a sync after the commit. Young in-flight and committed records are not cleared by this option.

`--purge` removes the configured replicas and their pending-write records for the **current identity**; they can be rebuilt on a later covered read. It prints the same pending-write warning. It does not purge other identities or revoke node-side grants. `--host <url>` selects the host and therefore the identity partition for a CLI invocation; use the relevant `--host` to inspect or purge data for another host partition. Purge covers the configured prefixes, not every saved prefix or every identity in the profile. Physical cleanup can retain a contentless SQLite generation/tombstone marker so previously opened handles fail closed.

The local identity partition is the canonical host, full space and principal (the signing identity). Different hosts, spaces or principals have separate replicas and pending-write state. In particular, changing `--host` does not reuse another host's local cache or read-your-writes state.

### List ordering and cursors

Local list keys are ordered by UTF-8 bytes. A node may order them differently: SQLite uses byte order, while production Postgres uses its database collation. Do not assume identical order across local and network list results.

Local pagination uses a `tcr1.` cursor bound to its space and list path. Node-issued cursors are served by the network. A pending write in the unread portion of a list range forces network fallback; with a local continuation cursor, it instead returns `INVALID_INPUT` with `meta.replication: "cursor_restart"`. Restart the list without that cursor. Other unsafe local continuations (for example, incomplete coverage or a space/path mismatch) also return this typed input error without making a network request. Do not mix pages from the local and network sources.

### Network-only reads

Use the KV read option `source: "network"` for checks whose answer must reflect the node, such as an existence check. It bypasses replica open, sync and local reads:

```ts
const result = await node.kv.get("notes/today.txt", { source: "network" });
```

`list()` accepts the same option. The CLI's secret and vault existence checks already use network-authoritative reads. This option is for reads; writes remain network writes.

### Revocation and security

Revocation is discovered at the next sync, not while the device is offline. Once a sync reports revocation, the local replica is blocked and purged; `tc replica report` shows the replica as `revoked`. Do not retry with the revoked device grant; obtain a new device.

Local delegation checks verify the signature, CID, audience and expiry, but **not the proof chain**. The node verifies the chain on every sync. Local checks are not a substitute for node verification.

`tc auth logout` removes legacy replicas and the flag-owned `replication/` directory for every identity partition by default, including its device keys, identity and pending-write files, and event log. Pass `--keep-replicas` to retain both local roots. Logout clears the local session; it does **not** revoke delegations or grants at the node, which remain valid until expiry unless separately revoked. Cleanup refuses unsafe symlinks or active sync leases; a cleanup failure can leave local files behind.

**Code-derived defaults and scope:** the CLI overrides the SDK defaults above (60 seconds / 10 seconds); the code defaults for node-sdk are 120 seconds / 5 seconds. CLI `--purge` addresses only the currently bound identity and configured prefixes, while logout removes all profile partitions. These specifics follow the Phase 1 implementation rather than the broader planning notes.

## Browser: open, grant, sync, and read locally

The explicit browser API is exported by `@tinycloud/replica/browser`. `@tinycloud/web-sdk`
does not wrap it; its read-through beta is configured separately, see [Web read-through](#web-read-through-beta-web-sdk). It does expose owner delegation
methods used here: `requestPermissions()` obtains the explicit KV authority and
`delegateTo()` issues it to the replica's device DID. The `owner` below is an
authenticated `TinyCloudWeb` instance configured with the app manifest needed
for permission requests.

```ts
import { openReplica } from "@tinycloud/replica/browser";

const replica = await openReplica({
  host: "https://tee.node.tinycloud.xyz",
  space: spaceId,
  prefix: "notes/",
  principal: signedInUserDid,
});

// The authenticated owner explicitly authorizes this prefix for the device.
const permission = [{
  service: "tinycloud.kv",
  space: spaceId,
  path: "notes/",
  actions: ["get", "sync"],
}] satisfies Parameters<typeof owner.delegateTo>[1];
const approval = await owner.requestPermissions(permission);
if (!approval.approved) throw new Error("The owner did not approve the replica grant.");
const issued = await owner.delegateTo(replica.deviceDid, permission, { expiry: "30d" });
// "30d" is a requested lifetime; the issued grant may expire sooner if the
// owner's session expires sooner.
await replica.installGrant(issued.delegation.delegationHeader.Authorization);
await replica.sync();

// Local read APIs never use the network; they still enforce grant expiry.
const read = await replica.get("notes/today.txt");
if (read.status === "present") {
  const text = new TextDecoder().decode(read.value);
  console.log(text);
}

const keys = await replica.list({ prefix: "notes/" });
console.log(keys.entries.map(({ key }) => key));

await replica.close();
```

`principal` is the signed-in user's identity DID and partitions data for users
sharing a browser origin; it is not an authorization check. The grant and the
node authorize sync. Browser data is stored in IndexedDB through a dedicated
worker. Browser `get` and `list` are explicitly local; call `sync()` to poll
for updates. Browser sync requires Web Locks (`navigator.locks`); without it,
`sync()` rejects with `RUNTIME_UNSUPPORTED`, but an existing replica can still
be read. If a browser does not support IndexedDB, opening the replica fails
instead of silently switching to non-durable in-memory storage.

## Web read-through (beta): web-sdk

The Phase 2 beta adds read-through to `TinyCloudWeb`. With `replication.enabled`, `kv.get()` and `kv.list()` calls under the configured prefixes are answered from an IndexedDB replica when it covers the key, and from the network otherwise. It is off by default; with the option unset, web-sdk behaves as before. Read sources, reason codes, and freshness follow [Where reads go](#where-reads-go) and [Freshness and offline reads](#freshness-and-offline-reads), except where this section says otherwise.

### Enable

```ts
import { TinyCloudWeb, registerReplicationLoaders } from "@tinycloud/web-sdk";
import { indexedDbReplicaStorage } from "@tinycloud/replica/kv-storage";

// The runtime and authority load lazily. Register them before the first sign-in.
registerReplicationLoaders({
  runtime: () => import("@tinycloud/node-sdk/replication/runtime"),
  authority: () => import("@tinycloud/node-sdk/replication/authority"),
});

const tcw = new TinyCloudWeb({
  replication: {
    enabled: true,
    prefixes: ["notes/"],
    storage: indexedDbReplicaStorage(),
  },
});
```

| Option | Purpose |
| --- | --- |
| `enabled` | Turns read-through on. Off by default. |
| `prefixes` | Folders to replicate. Required when enabled. |
| `storage` | Use `indexedDbReplicaStorage()`. Required when enabled. |
| `allowSecrets` | Opt-in for `vault/`, `/`, and the secrets space. |
| `grantTtlMs` | Lifetime cap for the replica grant. 24 hours by default; values above 7 days are rejected. |
| `maxBytes` | Origin-wide byte budget for replica data. See Storage budget below. |
| `syncIntervalMs`, `maxStalenessMs`, `staleSyncTimeoutMs` | Background sync (60 seconds), staleness limit (120 seconds), and stale-sync timeout (5 seconds). |
| `onEvent` | Receives replication read and write events. |

A restored session that does not cover replication asks for a fresh sign-in when the browser is online.

### Sign-out and account switch

- `signOut()` disables replication in this tab, and this tab serves no replica reads after it resolves. It does not end the in-memory web-sdk session (TC-1208), so do not treat it as full session teardown.
- Erasing the account's replica data runs in the background. `signOut()` does not wait for the erase. Other tabs are refused from their next database transaction and drop their open handles.
- On an account switch, the next account's replica stays inactive until every erase for the previous account completes. Its reads go to the network until then.
- A failed erase is retried at the next sign-in and on every page load. Until it completes, status reports `purge_pending`, and the affected partitions cannot be read.
- If the database cannot be written during sign-out, the SDK deletes the replica database. If that also fails, it writes a `localStorage` marker that stops activation and delivery in every tab. If neither works, cross-tab denial is not guaranteed; see Known limitations.

Unlike node-sdk, which keeps data on disk until `purge()` is called, a browser replica lives in a shared origin profile, so sign-out erases it.

### Grant lifetime

A replica grant's effective expiry is the earliest of:

- the grant's own expiry;
- the install time plus `grantTtlMs`;
- the consent deadline: the SIWE `issuedAt` of the sign-in that granted replication, plus 7 days.

Reads stop at the effective expiry. Expiry blocks reads but does not erase local data. When less than a quarter of the lifetime remains, the SDK renews the grant silently with the session key, without a wallet prompt. If renewal fails because the device is offline or the node refuses it, reads continue until the effective expiry. No renewal happens after the consent deadline; sign in again to refresh consent.

### Freshness and offline reads

The defaults are a 120-second maximum staleness, a 5-second stale-sync timeout, and a background sync every 60 seconds. Offline, a stale value is served with `syncError: "NETWORK_ERROR"`. To bypass the replica for one read:

```ts
const fresh = await tcw.kv.get("notes/today.txt", { source: "network" });
```

### Events and status

`onEvent` receives `replication.read` and `replication.write` events. `tcw.replication` provides `status()`, `sync()`, `purge()`, and `clearPending()`. Status adds two fields:

- `persisted` is the result of `navigator.storage.persist()`. `false` means the browser did not grant persistent storage for this origin.
- `purge_pending` reports an erase that has not finished, including one left over from an earlier account.

### Storage budget

`maxBytes` caps replica data for the whole origin, across all prefixes and accounts stored on it. A sync that would exceed the cap stops with `STORAGE_BUDGET`. A browser `QuotaExceededError` stops it with `STORAGE_FULL`. In both cases, committed content still serves covered keys while they are fresh, and stale or uncovered reads go to the network. Nothing is evicted.

The browser quota is shared with the app's other storage, so set `maxBytes` below the space the app needs for its own data. Private browsing and browsers without IndexedDB report `runtime_unsupported`, and every read goes to the network.

### Stored contents

Replicating `vault/`, `/`, or the secrets space requires `allowSecrets: true`, as in the node-sdk section. The replica stores values as written. Values outside `vault/` may be plaintext in IndexedDB on the device, so treat a shared browser profile accordingly. Sign-out erases them.

### Browser support and revocation

- Chromium is the qualified browser for this beta. WebKit runs are attempted and reported but not qualified. Other browsers, Tauri, and Capacitor are not qualified.
- A revocation reaches a device at its next sync. A device that stays offline keeps its data until the grant expires.
- Revocation through the SDK or CLI can fail for some grant shapes (TC-721, TC-821). Until those are fixed, rely on short `grantTtlMs` values.

## Security model

- A replica stores only its configured KV prefix, and the grant must cover
  that prefix; the grant may be broader. Out-of-scope names and bytes are not
  fetched into replica storage.
- By default, local reads stop when the node-attested grant window expires. A
  retention window attested by the node can allow reads after expiry. An
  offline device cannot discover an online revocation until it reconnects;
  once the replica learns that its serving grant was revoked, reads are
  blocked and content purge begins. If physical cleanup is pending, the next
  open retries it.
- CLI replica files use mode `0600` under directories with mode `0700`.
  Protect the device account and backups as well; file permissions do not
  protect against the same operating-system user.
- Sync grants do not grant decryption. Replicating the secrets space, a `vault/` folder, or `/` (the whole space) requires explicit opt-in: `tc replica sync --allow-secrets` on the CLI, or
  `openReplica({ allowSecrets: true })` in the explicit browser API, or
  `replication.allowSecrets: true` for web read-through. It copies encrypted
  secret material to the device. If you separately grant decrypt, note that
  decrypt authority is network-wide today, not limited to one secret name. Do
  not use it unless that scope is acceptable.
- **Since CLI 1.1.0:** `tc auth logout` deletes local replicas for that
  CLI profile by default; pass `--keep-replicas` to keep them. Logout does not
  revoke the profile's grants on the node. To revoke node-side authority, use
  `tc delegation revoke <cid>`. Logout refuses to remove replicas if a sync is
  running or the replicas directory is a symlink.

## Known limitations

- **Known node limitations being tracked (TC-737):** a quiet prefix in a busy
  space can make each poll scan newer changes outside that prefix, increasing
  sync work and potentially latency even when the prefix has no updates.
- **Known node limitations being tracked (TC-735):** on Postgres, blob uploads
  run inside the per-space write lock, so uploads can slow other writes in
  that space.
- Remote refresh is polling through `sync()`; there is no remote push or watch
  API. In the browser, `onCommitted` reports only local commits from other
  tabs.
- Replicas are read-only. Offline writes are not supported.
- **Web read-through (beta):** a device that stays offline keeps its replica data until the grant's effective expiry or the account signs out. It cannot learn about revocation before then.
- **Web read-through (beta):** revocation through the SDK or CLI can fail for some grant shapes (TC-721, TC-821). Until those are fixed, use short `grantTtlMs` values.
- **Web read-through (beta):** if both the replica database deletion and the sign-out marker fail, another open tab is not guaranteed to stop serving the previous account's replica.
- **Web read-through (beta):** WebKit runs are attempted but not qualified for this beta. Only Chromium is qualified.
