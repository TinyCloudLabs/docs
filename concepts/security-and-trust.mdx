TinyCloud is built around cryptographic proofs and attenuated capabilities. The safe default is to assume only what the linked docs and source explicitly establish.

## Encryption and operator access

TinyCloud capabilities control **who is authorized to act**. They do not by
themselves encrypt content or make the service unable to read it. The
[homepage mode comparison](/#privacy-at-a-glance) summarizes the choices.

- **Transport and storage:** HTTPS encrypts traffic to its TLS endpoint.
  Disk, database, backup or sealed-state encryption protects stored bytes,
  not plaintext in the process that can decrypt them. Do not assume every
  deployment encrypts every disk or backup.
- **Ordinary KV and SQL:** the SDK sends values, SQL and parameters to the
  node for processing. Unless the application encrypts content first, an
  ordinary node operator can read it. A space is an authorization boundary,
  not an encryption boundary.
- **Application E2EE:** this requires encryption before storage and keys
  available only to the intended endpoints. The SDK's wallet-derived vault
  mode encrypts and decrypts locally. Network-backed vault mode also encrypts
  values locally, but uses a node-mediated key-release/decrypt flow: its key
  service is an additional trust boundary. Do not describe both modes as
  “only the user can decrypt.” See [Data Vault](/concepts/data-vault).
- **Authorized clients:** a client, agent or recipient that receives
  plaintext can retain or disclose it. An AI provider's handling of tool
  results is a separate trust decision. Expiry and revocation stop future
  authorized access; they cannot recall copies already read.
- **Hosted MCP:** the service processes readable inputs and results,
  including delegated secret values. Its runtime and operator are in the
  trust boundary even when the node stores encrypted envelopes. Local
  CLI/stdio removes that hosted MCP hop, not the node or AI-client boundary.
- **Self-hosting:** choosing your own node or MCP operator changes whom you
  trust. It does not hide plaintext from that operator's administrators,
  runtime, logs or backups unless a separate verified protection does so.

### TEE and OpenKey limits

A trusted execution environment (TEE) is a server-side execution boundary,
not application E2EE. The protected program may handle plaintext or keys.
Protection from the infrastructure operator depends on hardware trust,
verification of a fresh attestation bound to the service/key, accepted code
measurements, key-release policy, and what the program exports or logs.
It does not protect plaintext sent onward to an authorized client.

OpenKey's production key-sealing implementation uses dstack-derived keys and
exposes bound quotes; its explicit local-development mode uses mock keys.
OpenKey-managed keys are unsealed for signing in the service runtime.
This is different from a wallet whose key stays exclusively on the user's
device. Passkey sign-in alone does not encrypt application records.

Neither a `tee` hostname, a deployment file, nor the existence of an
attestation endpoint proves that your client verified the running deployment.
These docs do not certify a live deployment or promise that every SDK/MCP
request verifies hardware attestation. Check the actual verifier, accepted
measurements and deployment policy before relying on operator exclusion.

## What TinyCloud verifies

- A signer proves control of the wallet or key that signs the SIWE flow.
- The session carries capabilities that bound what it may do.
- Delegations must stay within the parent capability's scope.
- The generated capability registry records the exact action names, aliases, and statuses that the node currently accepts.

## What TinyCloud does not hand you for free

- A session DID is not a durable user identity. Use `tc.did` after `signIn()` when you need the owner's DID.
- An ability listed in the whitepaper is not automatically a shipped action. Check the generated registry and implementation docs.
- OpenKey OAuth is not the same thing as TinyCloud authentication. TinyCloud still uses SIWE for its own sign-in flow.
- Revoking a bearer Share link stops new reads, but cannot recall copies already downloaded. Anyone holding the complete URL can read it until then. Use an addressed share when only one person or domain should read it.
- An HTML page shared as a bearer link runs in a sandboxed frame. It cannot read the link or the viewer's session, but it can reveal the reader's IP address to the sender.

## Trust boundaries

| Boundary | Safe assumption | Read more |
| --- | --- | --- |
| Identity | `tc.did` becomes the owner DID after sign-in; `tc.sessionDid` remains the ephemeral session key DID. | [DID Formats](/concepts/did-formats) |
| Authorization | Capabilities are delegated, scoped, and revocable. | [Capabilities](/concepts/capabilities) and [Delegations](/guides/delegations) |
| Storage | Ordinary node operators can read unencrypted values; application encryption and network-backed key release have separate trust boundaries. | [Spaces](/guides/spaces) and [Data Vault](/concepts/data-vault) |
| App requests | Manifests describe requested permissions and delegation targets before sign-in. | [App manifests](/concepts/app-manifests) |
| Sharing | Browsers omit a URL fragment from the HTTP request, but client code can read it. Addressed shares use encryption and a signed policy at the owner's node. Keep complete links out of logs and messages to unintended recipients. | [Share files](/cli/share) |
| Agents | An agent holds only what the owner approved for its profile through OpenKey, and the owner sees each capability before approving. | [Agent skills](/guides/agent-skills) |

## Security posture

1. Treat the implementation docs as the source of truth for shipped behavior.
2. Treat the generated capability registry as the source of truth for ability names, aliases, and status.
3. Treat whitepaper material as normative only when it does not conflict with code-backed behavior.
4. Do not infer extra guarantees from a page layout, a proposal, or a marketing summary.
