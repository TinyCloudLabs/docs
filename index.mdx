# TinyCloud Documentation

TinyCloud lets browser and backend applications store user-owned KV and SQL
data in isolated spaces, then share access through scoped capabilities. These
docs are for application developers, protocol integrators, and node operators.

TinyCloud is designed for data the user should own and control. It is not a
replacement for every application database, especially when the application
operator must own all data and access policy.

## Privacy at a glance

User-owned access is not the same as end-to-end encryption (E2EE).
Choose the trust boundary for the actual data path:

| Mode | Who can see plaintext? |
| --- | --- |
| HTTPS / encrypted disks or backups | HTTPS protects traffic in transit; storage encryption protects stored bytes. Neither hides data from the service processing it. Storage protection depends on the deployment. |
| Ordinary KV / SQL | The node processes readable values and queries unless the app encrypts values first. An ordinary node operator can access that plaintext. |
| Application E2EE | Only endpoints holding the decryption keys, **if** the app keeps those keys out of the storage service. This is not the default for all TinyCloud data; metadata may remain visible. |
| Hosted MCP | MCP processes tool inputs and results, including secrets it is authorized to decrypt. Its runtime/operator and the connected AI client are in the trust boundary. |
| Attested TEE processing | Plaintext or keys may exist inside the trusted runtime. Protection from infrastructure operators depends on verified attestation, approved code and key-release policy; a `tee` hostname is not proof or app E2EE. |
| Self-hosted | You choose the operator; ordinary node/MCP administrators can still access plaintext processed there. Self-hosting does not add E2EE. |

See [Security and trust](/concepts/security-and-trust) for encryption modes,
authorized clients, OpenKey and attestation limits.
